# Product

## Platform

web

## Users

Primary user: World of Warcraft guild officers and guild masters (GMs) — the people administering a guild's roster, ranks, roles, and events. This is admin-tool usage: reviewing/resolving roster matches, configuring role-automation rules, watching an audit log, managing bot behavior per guild.

Secondary (future, currently minimal): regular guild members, who can sign in and see a role-gated subset of information (some pages/data are hidden to everyone but GMs/officers). Very little exists for this audience today — most of the app is officer/GM-facing.

## Product Purpose

GuildThing is a guild-management webtool for WoW guilds, paired with a companion Discord bot and an in-game addon, sharing one database. It exists to remove the manual busywork of keeping a guild's roster, Discord roles/channels, and in-game character data in sync — work guilds otherwise do by hand across spreadsheets, Discord bots, and addons that don't talk to each other.

## Positioning

The mechanism a neighboring product (a Discord scheduling bot, a spreadsheet, RaiderIO) can't truthfully copy: GuildThing is one system spanning the web app, the Discord bot, and the in-game addon, sharing a single source of truth. Roster membership, ranks, roles, and character data stay in sync across all three surfaces instead of being re-entered or reconciled by hand in each one.

## Operating Context

- Self-hosted: deployed via Docker Compose (or local Node/pnpm) by whoever runs it for their guild(s). One instance can be opened to host multiple guilds depending on `InstanceSettings.guildCreationMode` (`owner` / `allowlist` / `public`), but defaults to owner-only.
- Auth via Discord OAuth (Better Auth) — a user's Discord identity is the login.
- Core web surfaces observed in the route tree: guild roster, events, sync (external character sync), bot configuration/admin, addon-related settings, profession pages, guild-level settings, audit log.
- Roster/role automation domain concepts from the schema: roster members, pending roster matches (auto-match vs. manual resolution), PUG members, protected roles, inactivity target roles, role-change/rank-change history, configurable role rules (grant roles/channels based on conditions), external character sync, member nicknames/activity, onboarding questions.
- The Discord bot enforces a per-guild automation kill switch (`botEnabled`) — officers can pause background automation (role sync, channel grants, external sync, inactivity filter) without it being a full outage switch; live slash commands keep working.
- Companion in-game addon (Lua, `apps/addon`) and Discord bot (`apps/bot`) are separate deployables sharing the same Prisma/SQLite database as this web app — this PRODUCT.md is scoped to `apps/web` only, per the user's choice not to write one product record for the whole monorepo.

## Capabilities and Constraints

- Confirmed functionality: roster management with manual conflict/match resolution, role-based automation rules (grant Discord roles/channels on conditions), guild event management, external character sync (against Wowhead data), per-guild bot enable/disable, audit logging of role/rank changes, API keys per guild, member-facing role-gated views (currently minimal).
- Role-gated UI already exists at the framework level (some content visible only to GMs/officers, other content visible to regular signed-in members) — future member-facing surfaces should build on this rather than introduce a new permissions model.
- Undecided: what a "regular member" experience should eventually contain — today there's little for that audience beyond sign-in and a role-gated view of select information.

## Product Principles

1. One shared source of truth across web, bot, and addon — never design a web-only feature that would force a guild to re-enter or reconcile data on another surface.
2. Officer/GM is the default audience for now — optimize for admin task completion (roster triage, rule configuration, audit review) over broad approachability, until member-facing surfaces are actually scoped.
3. Automation must stay legible and reversible — officers need to see what the bot did/will do (audit log) and be able to pause it (kill switch) without losing manual control.
4. Self-hosted, variable-trust deployments — an instance may be owner-only or opened to the public; the product must not assume a single trusted operator per deployment.
